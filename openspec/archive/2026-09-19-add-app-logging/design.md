# Design: add-app-logging

## Context
Нужен минимальный, самодостаточный журнал без внешних сервисов. Логи должны переживать перезапуск приложения и не расти бесконечно. Экран — про просмотр и фильтрацию, не про настройку того, что сохраняется.

## Goals / Non-Goals
- Goals: надёжная запись в файл, разумный лимит, простой экран с фильтром, пригодные для диагностики сообщения.
- Non-Goals: телеметрия/отправка в сеть, структурированный JSON-экспорт, уровни сверх `debug/info/error`, `logcat`-интеграция.

## Decisions

### Модель
```dart
enum AppLogLevel { debug, info, error } // порядок = возрастание важности

class LogEntry {
  final DateTime time;
  final AppLogLevel level;
  final String message;
  final String? error;      // toString исключения
  final String? stackTrace; // опционально
}
```

### Абстракция и реализация
- `AppLogger` (интерфейс): `debug/info/error(...)`, `Stream<LogEntry> get stream`, `Future<List<LogEntry>> readAll()`, `Future<void> clear()`.
- `FileAppLogger` (реализация):
  - **все** записи немедленно дописываются в `<appSupport>/logs/app.log`;
  - держит `StreamController<LogEntry>.broadcast()`, чтобы экран обновлялся в реальном времени;
  - параллельная запись сериализуется очередью (`Future`-цепочкой), чтобы не было гонок при ротации.
- `NoopAppLogger` — для тестов и платформ без ФС.

### Ограничение размера (ротация)
- Порог одного файла: `maxFileBytes = 512 KB`.
- При превышении: `app.log` → `app.log.1` → `app.log.2`, старейший удаляется.
- Хранится `maxBackups = 3` бэкапов, т.е. суммарный потолок ≈ 2 МБ. Это «разумный лимит»: достаточно истории, но не разрастается.
- Проверка размера — перед записью (по текущему размеру файла), без чтения всего файла.
- `clear()` удаляет все файлы журнала.

### Экран и фильтр
- Экран `/logs` показывает записи из памяти-буфера + догружает `readAll()` из файла при открытии.
- Выпадающий уровень (по умолчанию `info`) задаёт **порог отображения**: `error` → только ошибки, `info` → info+error, `debug` → все. Фильтр применяется только к показу; в файл всегда пишутся все уровни.
- Действия: обновить (перечитать файл), очистить (с подтверждением).
- Быстрый доступ — из меню на экране библиотеки.

### Формат строки
`2026-09-19T12:34:56.789Z INFO  message (error=..., stack=...)` — простой текст, удобный для `adb pull` и глазной диагностики.

### Интеграция
- Ключевые точки: ошибки инициализации/воспроизведения плеера и fallback на кэш, ошибки `StorageProvider` (сеть/авторизация), ошибки импорта книги, подключение/отключение хранилища.
- В UI-сообщения ничего не ломаем: логгер дополняет, а не заменяет сообщения.

## Risks
- Запись на диск в UI-потоке — операции маленькие и асинхронные, но при частых событиях возможна конкуренция; сериализуем очередь и не логируем высокочастотные события без нужды.
- Ротация на каждом событии даёт лишние `stat`; проверяем размер не чаще, чем раз в запись, это приемлемо.
- Пользователь может прислать лог с чувствительными данными (URL хранилища, логин). Пароль в логи не пишем; URL/логин — только если попали в сообщение, стараемся не логировать учётные данные.
